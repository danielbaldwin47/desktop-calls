# Telephony API quirks

Known misbehaviour of `org.pipewire.Telephony` and obexd PBAP. Each one should become a Simulated Phone scenario. Terms are as in [GLOSSARY.md](../../GLOSSARY.md).

- 2026-11-04, from Foner at `AminBlg/kaller@fc25b13`: `Call1.Hangup` returned "Method doesn't exist" on Foner's handset, while `org.ofono.VoiceCall.Hangup` on the same object worked. The PipeWire 1.6.9 source appears correct ([HFP research](../research/2026-11-04-hfp-stack.md) §1.3). Treat it as a handset quirk that needs a fallback.
- 2026-11-04, same source: `GetManagedObjects` does not list Calls, and `GetCalls` briefly returns an empty list during dialling. Track Calls through `InterfacesAdded`/`InterfacesRemoved` signals, not polling.
- 2026-11-04, same source: withheld (private) numbers arrive as an empty line identification. Foner silently drops those missed Calls; we must not.
- 2026-11-04, same source: obexd PBAP allows one session at a time, and Call History timestamps carry no timezone.
- 2026-11-04, from [HFP research](../research/2026-11-04-hfp-stack.md): there is no `Deactivate()`, so Handoff to the Phone needs a workaround. The Phone's contacts permission prompt times out after 30 s.

Full detail: [Foner evaluation](../research/2026-11-04-foner-evaluation.md).
- 2026-11-04, verified on the real Pixel 9a ([first connection](../research/2026-11-04-first-phone-connection.md)): the Phone's AudioGateway object exists only once the hands-free link is fully set up, and it was `ag1`, not `ag0`. PipeWire's `Introspect` lists no child nodes, so `busctl --user tree` **never** shows it. This supersedes the "next step" in [HFP research](../research/2026-11-04-hfp-stack.md), which suggested `busctl tree`. Discover Phones with `GetManagedObjects` plus `InterfacesAdded`/`InterfacesRemoved`, and match on `Address`. `GetModems` returns an empty property list.
- 2026-11-04, verified on the real Pixel ([Handoff prototype](../research/2026-11-04-handoff-to-phone-prototype.md), `5d811f6`): `Activate()` does nothing while `RejectSCO=true`. Set it false, call `Activate()`, then set it true again. The Pixel ignored `Activate()` once in 7 tries, so wait 3 s and retry once. During a Handoff-to-Phone profile bounce, the Call object vanishes without reaching `disconnected` and returns `active` 0.5–1.0 s later; treat it as the same Call ([ADR-0005](../adr/0005-handoff-to-the-phone-bounces-the-hands-free-profile.md)). A malformed `Properties.Set` crashes WirePlumber, which has no signature check; an upstream report is not filed.
- 2026-11-04, PipeWire 1.6.9 source map (from the #3 retro, to save re-fetching): `ag_properties_set` in `spa/plugins/bluez5/telephony.c` around line 862 (no variant type check, hence the crash); `hfp_hf_transport_activate` in `spa/plugins/bluez5/backend-native.c` around line 1888; `Activate()` does not lift `RejectSCO`. Source tree: https://gitlab.freedesktop.org/pipewire/pipewire/-/tree/1.6.9/spa/plugins/bluez5
- 2026-11-04, verified on the real Pixel ([conformance](../research/2026-11-04-conformance.md), PR #37): `InterfacesAdded`/`InterfacesRemoved` name exactly `AudioGateway1` and `AudioGatewayTransport1` for an AudioGateway, and only `Call1` for a Call. After a WirePlumber restart, Telephony returns in about 1.07 s with **the same object paths under a new bus owner**, so track `NameOwnerChanged`. `Battery1` comes and goes with hands-free. Follow-ups are filed on #7, #9, #19 and #20.
- 2026-11-05, from source reading, not yet checked on the Pixel ([mute and keypad](../research/2026-11-04-mute-and-keypad.md), PR #50, `7bb6733`): PipeWire's `SendTones` sends its whole string as one `AT+VTS`, and Android's AT handler rejects any `AT+VTS` longer than one tone. The app sends one `SendTones` call per tone. Mute writes `MicrophoneVolume=0` and restores the previous value afterwards, or 15 if the Phone reported -1 (which arrives as 255). Whether the far end then hears silence is unverified ([#51](https://github.com/danielbaldwin47/desktop-calls/issues/51)).
- 2026-11-05, from [answered on phone](../research/2026-11-04-answered-on-phone.md) (PR #46, `b1c8b3e`): what the Pixel sends when a Call is answered or declined on the Phone is modelled in the Simulated Phone but not yet observed on the Pixel. Real-Phone Checklist group 2 (#28) covers it.
- 2026-11-05, from [out of range](../research/2026-11-05-out-of-range.md) (#19, `6bf11cb`): the app takes the Phone's presence from BlueZ's `Device1.Connected`, not from the AudioGateway, because an AudioGateway also goes away during the Handoff bounce and on a WirePlumber restart while the device stays connected. It reconnects with `Device1.Connect` (ADR-0004). Verified on the Desktop in #6: a page to an absent Phone fails after BlueZ's page timeout of 5.12 s. Inferred, not seen from the Pixel: "pairing lost" arrives as `org.bluez.Error.Failed` "br-connection-key-missing", `AuthenticationFailed` or `AuthenticationRejected`; the link supervision timeout; and whether `Connect` also brings A2DP back. Real-Phone Checklist items for all three are in that note, for the user only.
- 2026-11-05, from [hands-free not back](../research/2026-11-05-handsfree-not-back.md) (#101, `f7a35a6`): when hands-free is missing but the Phone is still connected, the app retries with `Device1.ConnectProfile(HFP AG)` (the call ADR-0005 allows; dated note in ADR-0005, `83e378b`), after 1 s, 2 s, then every 3 s. `AlreadyConnected` and `InProgress` count as success. What `Device1.Connect` does on a connected device with one profile down is unverified. The Simulated Phone gained the quirks `connect-profile-fails` and `connect-profile-fails-once`; their error text "br-connection-refused" is inferred, not seen from the Pixel. Nothing safe provokes this failure on the real Pixel, so the Checklist has no item for it.
- 2026-11-05, from [identifying caller](../research/2026-11-05-identifying-caller.md) (#103, `f6ecaae`): a Phone without `+CLCC` reports the number with the `+CLIP` after the first `RING`, so a Call can appear with no number and gain it about 1 s later (the Simulated Phone's `late-line-identification` quirk). The app waits 2 s before calling it withheld. That the Pixel's number comes within 2 s is inferred.
- 2026-11-05, from PipeWire 1.6.9 source, not yet checked on the Pixel ([call waiting](../research/2026-11-05-call-waiting.md), #16): `Call1.Answer` refuses a `waiting` Call, so answer one with `HoldAndAnswer` (`AT+CHLD=2`) or `ReleaseAndAnswer` (`AT+CHLD=1`); both need an `active` Call, so while the user's own Call is still `dialing` or `alerting`, hang that up and `Answer` once the Call goes `incoming`. Without `CHLD` support all three reply `NotSupported`. `Hangup` on the active Call while another is held sends `AT+CHLD=1`, so the held Call becomes active, unless a Call is `waiting`: then `AT+CHLD=1` accepts the Waiting Call instead (27.007), so the app refuses that Hang up. While a Call is `waiting`, `AT+CHLD` acts on it first: `Hangup` on a held Call (`AT+CHLD=0`) declines it, and `SwapCalls` (`AT+CHLD=2`) answers it, which is how the app answers it beside a lone held Call. No `AT+CHLD` names a Call (PipeWire sends no `AT+CHLD=1x`), so End & Answer with one Call held and one live relies on `AT+CHLD=1` leaving the held Call alone.
- 2026-11-05, mostly inferred; the restart behaviour is not observed on a real WirePlumber restart ([ADR-0007](../adr/0007-a-vanished-call-is-settled-by-the-phones-calls-once-hands-free-is-back.md), PRs #174 and #176): after hands-free returns, the AudioGateway reappears first and its Calls follow, 30 to 60 ms later on the Pixel and later on a loaded Desktop (both as ADR-0007 states them); PipeWire's Telephony API has no "listing complete" signal. A WirePlumber restart removes Calls without `disconnected`, so a Hang up sent just before it may never reach the Phone; a method call pending on the old service is answered by dbus-daemon with `NoReply` "Message recipient disconnected from message bus without replying" (the Simulated Phone does this; dbus-broker's wording is inferred, #154). The Simulated Phone's quirks `calls-listed-late` and `hangup-unanswered-once` model both.
