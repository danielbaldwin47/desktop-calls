# The gallery's "Call ended" race: recording the screen on change

Date: 2026-11-05. Ticket #42, part 1 (`just merge`, part 2, is PR #56). Follows [the CI banner latency note](2026-11-04-ci-banner-latency.md), §4.
Legend: **[V]** = verified (where is stated). **[I]** = inferred, not tested.

**Bottom line:** the gallery missed "Call ended" because it sampled the screen with `grim` at intervals set by its own slow work, while the app, starved of CPU, drew that state late and briefly. `screenshot_when` now records the screen through wlr-screencopy with damage: one frame of the screen as it is, then one frame each time the compositor reports a change, judged in order. Any state the compositor shows for longer than the moment between two requests reaches `shown`, and a still screen costs no CPU.

## The race and the fix

The CI-like loop used below: the gallery test (`cargo test -p automation --test gallery`) pinned with `taskset -c 0` to one CPU shared with N busy loops, inside `unshare -rm` with a tmpfs over `/dev/dri` (GPU hidden) and a 64 MB tmpfs over `/dev/shm`, and `TMPDIR` set apart because other agents' runs were deleting `/tmp/desktop-calls-test-*` mid-scenario. Other agents' builds loaded the remaining CPUs throughout, so timings varied run to run.

- **Before:** with 12 busy loops the old gallery failed on its first run with CI's message, `the screen never showed call-window-ended-light within 10s`. With 3 it passed 3 of 3, as the earlier note found. **[V]**
- **Why it failed.** `screenshot_when` captured with `grim`, ran `shown` (two `region_where` passes over 8.3 million pixels in a debug build), then captured again. Each `grim` run also made sway render the 4K output with pixman, and `grim` encoded a 33 MB frame as PNG. **[V]** (code)
- **First attempt, not enough:** `grim` back to back on a thread, with `shown` judging the captures in order, failed 1 run in 18 with 3 busy loops. The kept captures showed why: one `grim` run took 1.0 to 1.3 s, and 1.4 s after the app logged `call-ended`, the screen still showed the live Call Window (red Hang up, `0:00`). The next capture already showed the window closed. Capturing to PPM to skip PNG encoding (about 0.5 s a capture) still failed 1 run in 15. Continuous capturing kept sway and `grim` busy on the one CPU the app needed to draw. **[V]**
- **Fix:** `crates/test-harness/src/screencopy.rs` speaks `zwlr_screencopy_manager_v1` version 2 on the harness's own Wayland connection. The first request is a plain `copy`; each later one is `copy_with_damage`, which sway completes only after the screen changes. Two shared-memory buffers take turns, so the next request is sent before the last frame is read out. Frames are written as PPM under the scenario's `captures/` directory, at most 8 wait for `shown`, rejected ones are deleted, and the chosen one is saved as `<name>.png`. The 2 s (`CALL_ENDED_MS`) is unchanged, and nothing retries. `grim` remains for plain `Harness::screenshot`. **[V]**
- **After, better but not proven:** the loop ran niced (`nice -n 19`) with 3 busy loops, as other agents needed the CPUs. One run of 20 stopped at once on the gallery's separate muted-state race (`MuteUnavailable`: Mute pressed before the Call's audio was here), which #61 fixed; this branch now has it from main. With a wait for the audio added locally: 12 passes, then an outside SIGTERM killed run 13 after its test passed; then 3 passes and a miss, `the screen never showed call-window-ended-omarchy-dark within 10s`. **[V]**
- **Why that run missed:** the app logged `call-ended` at :21.27 and the recorder connected 0.5 s later, but sway delivered its first frame at :24.68, after the 2 s had ended; the next frame shows the window closed. Sway itself got no CPU for the whole 2 s, so no capture method could have seen the state. That run took 189 s against about 85 s usual: at nice 19 the test yields to other agents' nice-0 builds, which CI's runner doesn't have. **[V]** (`captures/` file times and the app log)
- **The proof instead:** so a count of gallery runs measured other agents' load, the chief of staff replaced "20 in a row" on #42 with a deterministic test. `screenshot_when_catches_a_state_shown_for_200_ms` (`crates/test-harness/tests/screen.rs`) shows the test client's window for 200 ms, from start to end while `shown` is still judging the first frame, and requires a frame showing it. It passed 3 of 3 with recording; with main's sampling `screenshot_when` it failed with `the screen never showed brief-window within 10s`. **[V]**
- Damage that arrives while no request is pending completes the next request at once in wlroots, so a frame is missed only if a state appears and goes within the moment between two requests. **[I]** (from wlroots' screencopy behaviour as recalled, not read in its source here)
- **First match can be mid-resize:** in CI, `clicking_a_keypad_button_sends_its_tone` sent tone 4 instead of 1 (run 41979756259). It clicks where the frame `screenshot_when` returned showed the keypad, and the first frame whose Call Window had grown was not where it settled; `grim`, capturing late, had always seen the settled layout. `screenshot_when` now returns the latest frame of the matching run, once no new frame comes for 100 ms (`SETTLED`) or one stops matching, so a brief state is still caught. The test passed 3 of 3 locally afterwards. **[V]** for the failure and the local runs; **[I]** that the mid-resize frame was the cause.
