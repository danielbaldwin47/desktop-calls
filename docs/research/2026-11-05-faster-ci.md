# Faster CI

Date: 2026-11-05. Ticket #55. Every timing is from `gh run view <id> --json jobs`. Wall clock runs from the first job's start to the last job's end, and billable minutes are each job rounded up to a whole minute, as GitHub bills them.
Legend: **[V]** = verified (where is stated). **[I]** = inferred, not tested.

**Bottom line:** a warm-cache code-change run now takes 3.1 to 4.0 min of wall clock (4 runs), down from 5.4 to 7.5 min, for 1 or 2 more billable minutes (8 to 9 with the "Code changed?" job, against 6 to 8). A change to docs that no code reads is green in 13 s for 2 billable minutes, where it used to cost a full run of 6 to 8. With the "Code changed?" job in front, a code-change run bills 1 more minute (run 41981084029: 241 s, 9 minutes). The target set from the measurements is 3.5 min warm. Getting under 3 min would need a third runner or cargo-nextest: see Options.

## What made it slow, and what changed

1. **opt-level 3 for the whole harness.** #48 set `opt-level = 3` for `test-harness` and `automation`, for `region_where`'s pixel scan. It applies to each of the harness's test binaries too, so every run rebuilt them at opt-level 3: `just check` went from 27 s to 121 to 198 s. Rebuilding the workspace on two CPUs takes 49 s at opt-level 3, 47 s at 2, 16 s at 1 and 7 s at 0; one decode and scan of a 3840x2160 screenshot takes 7 ms at 3, 32 ms at 1 and 117 ms at 0. Now opt-level 1: 25 ms more per scan, against a 1 s deadline. The PNG crates stay at 3. **[V]** (local, `-j 2`, release-like timing loop; CI as above)
2. **Debuginfo.** Line tables only for our crates and none for dependencies. A cold build of every target on two CPUs took 126 s with full debuginfo, 102 s with line tables and 89 s with none; relinking after a harness change took 73, 46 and 41 s; the target directory, which the cache restores and saves, shrank from 2.8 to 1.7 GB (none: 0.9 GB). Backtraces keep file and line. **[V]** (local)
3. **A cache that matched in name only.** Swatinem/rust-cache keys on `Cargo.lock`, the crates' manifests and `rust-toolchain.toml`, not on the workspace `Cargo.toml` where the profiles live. After a profile change it restored a "full match" of stale artifacts, rebuilt everything (run 41976658980: build 140 s, lint 110 s) and, having matched, never saved. The workspace `Cargo.toml`'s hash is now in the key. **[V]** (runs 41976658980, 41977312703)
4. **The gallery rendered twice.** The gallery test rendered all 24 states into a temporary directory, then `just screenshot` rendered them again (23 to 40 s). The test now renders into `target/screenshots/gallery`, as `just screenshot` does, and CI keeps that. **[V]**
5. **One serial job.** `just check` and the tests now run as two jobs that start together. `just check` stays the one local entry point; CI runs `just check` and `just test` split by crate: `--exclude test-harness` in one job, every other crate excluded by name in the other, so a new crate runs in both rather than in neither. **[V]**
6. **base-devel.** It pulls in gdb, guile, perl and texinfo. CI now installs `gcc pkgconf`: `Cargo.lock` builds C only through `cc`, `pkg-config` and `system-deps`. Install time barely moved (19 to 24 s before, 17 to 21 s after). **[V]**

## Measured and not adopted

- **A prebuilt CI image on GHCR** (Arch, every package and the toolchain, 1.85 GB unpacked). Pulling and starting it took 31 to 55 s (mean 45 s, 8 runs); the stock image plus pacman plus rustup takes 37 to 47 s (mean 42 s). A hosted runner pulls the image afresh every time, so there is nothing to win. Removed. The package `ghcr.io/danielbaldwin47/desktop-calls-ci` is still on GHCR and may count against GitHub Free's 500 MB of Packages storage **[I]**; this session's token can't delete it (no `delete:packages` scope). **[V]** (runs 41972925926 to 41977312703)
- **A separate lint job** (`just lint` beside `just build`). It saved about 10 s warm and cost 2 billable minutes a run. Folded back into `just check`. **[V]**
- **mold.** The linker is already rust-lld (`readelf -p .comment`: "Linker: LLD 22.1.8"). **[V]**
- **sccache.** rust-cache already sets `CARGO_INCREMENTAL=0` and caches per ref; sccache's cache would be scoped the same way, and a dependency bump compiles new versions either way. **[I]**

## opt-level 1 and the screen recorder (#60)

#60 landed while this was open: the harness now records the screen on change, converting each 3840x2160 frame from the compositor's XRGB to RGB. At opt-level 1 the conversion, which pushed each pixel onto a `Vec`, took 160 ms a frame (40 ms at opt-level 3). The recorder hands the compositor its next buffer only once a frame is written, so on a busy runner it missed a window shown for 200 ms: `screenshot_when_catches_a_state_shown_for_200_ms` failed in run 41981986246. Locally, on two CPUs shared with a busy loop, the screen tests passed 2 and 4 of 10 times at opt-level 1, and 10 of 10 at opt-level 3. **[V]**

The conversion now writes into place through zipped iterators: 15 ms a frame at opt-level 1, faster than before at opt-level 3. Under the same load the screen tests pass 10 of 10. The 200 ms window is unchanged. **[V]** (local timings from temporary prints, since removed)

## For `just merge` (#42)

- **One workflow decides.** A first job, "Code changed?", runs `tools/changes.py` on the change. The rule is the one `just merge` already used for the commits a PR may lack, now shared from that file: docs are files under `docs/` or ending in `.md`, unless a file outside them names the path or a directory holding it. Both Rust jobs need it and run only when code changed. **[V]** (one-file probe commits: `docs/wiki/polish-scorecard.md`, the D-Bus snapshot and `CODING_STANDARDS.md` count as code; `docs/wiki/index.md` and `GLOSSARY.md` don't)
- **"CI passed" needs every job**, so it has no check until they have all finished. It fails unless "Code changed?" succeeded and both halves succeeded, or were skipped because "Code changed?" found docs alone. **[V]**
- **The first design was racy.** A separate `ci-markdown.yml` gave Markdown-only PRs their "CI passed", but on a PR that changed both, that check passed in 3 s, possibly before `ci.yml`'s jobs had checks. Replaced by the above. **[V]** (#62)
- **`just merge` counts every unfinished workflow run on the head as pending**, even when checks exist. A job gets its check only when it starts, so between "Code changed?" passing and the Rust jobs starting, every listed check has passed. It also counts a skipped check as passed only beside a passed "CI passed". **[V]**
- **Probe, docs only** (#63, run 41981110956): green in 13 s, Rust jobs skipped; `just merge 63 --wait 0` got past the checks and refused only because the PR was a draft. **[V]**
- **Probe, docs and code** (#64, run 41981113293): "CI passed" first appeared, pending, at 06:39:03, the snapshot in which the second Rust job had passed; `just merge 64` waited from 06:32:50 until the run finished, then refused at 06:39:08 only because the PR was a draft. **[V]**

## Minutes

From the start of CI (2026-11-04) to 06:00 on 2026-11-05, excluding this ticket's branch: 76 runs used 294 billable minutes, about 235 a day against 2,000 a month. 26 of those runs (97 minutes) changed only Markdown; 16 were pushes to main (51 minutes). Those now cost 2 minutes ("Code changed?" and "CI passed", 13 s in all). A code-change run costs about the same as before: 7 to 8 minutes for the two halves, plus 1 for "Code changed?" (run 41981084029: 241 s, 9 minutes). A run that misses the cache, after a change to `Cargo.lock`, `Cargo.toml` or the toolchain, costs about 14 minutes; the first run on main after this merges will be one. **[V]** (`gh api` over every run's jobs)

## Options (not taken: they change settings, billing or runners)

- **Make the repo public.** Standard hosted runners are free and unmetered for public repos, and their Linux runners have 4 vCPUs instead of 2. The build steps scale with CPUs, so warm runs would likely fall to about 2 min, and the minute budget would stop mattering, which would make a third shard free. **[I]** (GitHub's documented runner specs)
- **A self-hosted runner** on a spare machine. No minutes billed, a target directory that persists between runs (no cache restore or save, incremental rebuilds), and as many CPUs as the machine has: probably under 2 min. It costs upkeep and a machine that runs this repo's code. **[I]**
- **cargo-nextest.** Runs every test binary's tests in one pool instead of one binary at a time; the harness's binaries ran 95 s back to back in run 41978282402. It would add a tool and change `just test`, and more parallel screen scenarios on two CPUs might strain the 1 s deadlines, so it needs its own measurement. **[I]**
