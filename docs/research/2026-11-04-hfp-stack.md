# Research: Android phone calls on a Linux desktop via Bluetooth HFP

Date: 2026-11-04. Target: Arch/Omarchy, Hyprland, PipeWire.
Legend: **[V]** = verified against source code, docs, or this machine. **[I]** = inferred, not tested.

**Bottom line:** the working hypothesis holds, and it is easier than it looked. PipeWire 1.4+
ships the HFP Hands-Free (HF) role *and* a call-control D-Bus API (`org.pipewire.Telephony`).
This machine already runs that service. No Android app and no AT-command code are needed.
The app is a D-Bus client of PipeWire (calls) plus a client of obexd (contacts and call history).

## 1. PipeWire native backend: HF role and call control

### 1.1 HF role (desktop acts as the hands-free unit)
- **[V] HF role exists since PipeWire 0.3.22 (2021-02-18).** Commit `0b2d3730` "bluez5: Add HFP HF support" (Frédéric Danis, 2021-01-22) registers `/Profile/HFPHF` for UUID `0000111e` and sends `AT+BRSF`.
  mSBC in HF role: commit `01b6dbfc` (2021-02-16), same release.
  Source: https://gitlab.freedesktop.org/pipewire/pipewire/-/commit/0b2d3730b6b9c5b5a9f2b9b6748a6ad092d38ef4 ; https://gitlab.freedesktop.org/pipewire/pipewire/-/commit/01b6dbfca69b7d5e4a5d38ded0c8e1ff6d91f084 ; NEWS "0.3.28 … Add HFP HF support" https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/1.6.9/NEWS
  Until 1.4, the HF role carried audio only, with no call control.
- **[V] Call handling in the HF role (dial, answer, hangup, +CLIP caller ID, 3-way calls, AT reply handling) was added in July 2024 and first shipped in 1.3.82.** Commits `224f6a10` "Add call support in HFP HF" (2024-07-09), `18c447b0` (3-way), `61302113` (AT replies).
  https://gitlab.freedesktop.org/pipewire/pipewire/-/commit/224f6a10f5a02392d101d13fe8b15e743f8c01c1
- **[V] Configuration.** `bluez5.roles` includes `hfp_hf` by default. Default list in 1.6.9 docs: `[ a2dp_sink a2dp_source bap_sink bap_source bap_bcast_sink bap_bcast_source hfp_hf hfp_ag ]`.
  `bluez5.hfphsp-backend` defaults to `native`. Allowed values: `any, none, hsphfpd, ofono, native`.
  https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/1.6.9/doc/dox/config/pipewire-props.7.md (Monitor properties) ; WirePlumber 0.5.18 `docs/rst/daemon/configuration/bluetooth.rst`.
  Config goes in `~/.config/wireplumber/wireplumber.conf.d/*.conf` under `monitor.bluez.properties = { ... }`.

### 1.2 Telephony D-Bus API: it exists
- **[V] Added in PipeWire 1.3.82 (2025-02-05/06). First stable release: 1.4.0 (2025-03-06).** NEWS 1.3.82: "Add a Telephony DBUS API". NEWS 1.4.0: "A new Telephony D-BUS API compatible with ofono was added." NEWS 1.5.81 (2025-10-16): "Telephony improvements."
  Main commit: `b28399ac` "bluez5: add telephony D-Bus service implementation" (George Kiagiadakis, Collabora, 2024-07-08). oFono compatibility: `159846d2` (2024-09-11). Transport codec and state: `63e1c48c` (2024-10-17). RejectSCO/Activate: `b8e202f0` (2024-12-05).
  https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/1.6.9/NEWS ; https://gitlab.freedesktop.org/pipewire/pipewire/-/commit/b28399ac578357e838197590bb27c2480080bbb0
- **[V] Specification:** `spa/plugins/bluez5/README-Telephony.md` (1.6.9), https://gitlab.freedesktop.org/pipewire/pipewire/-/blob/1.6.9/spa/plugins/bluez5/README-Telephony.md . The interface XML below is from `spa/plugins/bluez5/telephony.c` and the installed `.so`.
- **[V] Enabled by default.** `service_enabled = true` (telephony.c:408). It runs on the **user session bus**, inside the WirePlumber process.

**Service** `org.pipewire.Telephony` (or `org.ofono` on the system bus when `bluez5.telephony.provide-ofono=true`)

| Object | Path | Interfaces | Members |
|---|---|---|---|
| Manager | `/org/pipewire/Telephony` (`/` in oFono mode) | `org.ofono.Manager`, `org.freedesktop.DBus.ObjectManager` | `GetModems() → a{oa{sv}}`; signals `ModemAdded(o, a{sv})`, `ModemRemoved(o)`; `InterfacesAdded/Removed` |

Errors: `org.pipewire.Telephony.Error.{InvalidState,InvalidFormat,NotSupported,InProgress,CME,Failed}`.
`AudioGatewayTransport1` is **not** in the README. It is defined in telephony.c (lines 21, 126-127) and appears in the installed binary.

- **[V] Call-audio transfer semantics** (commit `b8e202f0` message, and backend-native.c:1888-1910, 3015-3017):
  - `RejectSCO=true` makes PipeWire refuse the phone's incoming SCO connection, so the audio stays on the phone. The default comes from `bluez5.telephony.default-reject-sco` (default `false`).
  - `Activate()` sends `AT+BCC` (Bluetooth Codec Connection), which asks the phone to open SCO, so the audio moves to the desktop. Without codec negotiation, PipeWire opens a CVSD SCO link itself.
  - **There is no `Deactivate()`.** The API cannot move audio from the desktop back to the phone (see §5).
- **[V] Audio routing is automatic.** When the remote is an AG (`headset-audio-gateway` profile), the bluez source node is created as `Stream/Output/Audio` and the sink as `Stream/Input/Audio`, both with `node.autoconnect=true`. WirePlumber links them to the default speakers and microphone like any app stream.
  Sources: pipewire 1.6.9 `media-source.c:1299`, `media-sink.c:2666`; wireplumber 0.5.18 `src/scripts/monitors/bluez/name-node.lua:65`, `create-node.lua:34`.
- **[V] One card profile carries both music and calls.** PipeWire's card profile `audio-gateway` is "Audio Gateway (A2DP Source & HSP/HFP AG)", so phone music (A2DP) and call audio (HFP) coexist on one card. Source: `bluez5-device.c:2025-2033`.
- **[V] Not exposed:** HFP indicators (signal strength, battery, roaming, operator). `AudioGateway1` has no such properties (telephony.c introspection XML).

### 1.3 Field reports on the API (secondary sources, single handsets)
- Foner (AminBlg, KDE dialer built on this API; log dated 2026-08-09, PipeWire 1.6.8, BlueZ 5.87, Samsung Android). Dial, answer and hang up work; `AudioGatewayTransport1.Codec = 2` (mSBC); transport `State` goes idle→active during a call. They reported `Call1.Hangup` returning "Method doesn't exist" while `org.ofono.VoiceCall.Hangup` worked.
  **[V] 1.6.9 source dispatches `Call1.Hangup`** (telephony.c:1633), so this is probably a race against an object that had already been removed. Treat it as unconfirmed. https://github.com/AminBlg/kaller/blob/main/docs/M0-selfio-notes.md
- Calls are announced on the **AG object's** ObjectManager, not the manager's. This is consistent with the README, which says the AG object implements ObjectManager. Subscribe to `InterfacesAdded/Removed` on each AG path, or to oFono `CallAdded/CallRemoved`.

## 3. Audio quality

- **[V] HF role advertises every available codec** via `AT+BAC=1,<ids>`: CVSD=1, mSBC=2, LC3-SWB=3. LC3-A127 (24 kHz, Apple) is also implemented. Source: backend-native.c:2398-2408.
  Release history: LC3-SWB in NEWS 1.1.81 (2024-05-16, shipped in 1.2.0); LC3-24kHz in NEWS 1.5.81 (2025-10-16).
- **[V] Adapter requirements** (backend-native.c:905-960, `bluez-hardware.conf`):
  - mSBC/LC3-SWB need a transparent eSCO-capable controller (LMP features `TRSP_SCO` + `ESCO`, probed in `hci.c:63`) and USB alt setting 6 with isochronous endpoints (checked via libusb).
  - mSBC can also use alt 1 on kernels ≥5.8 (most), or alt1-rtl on Realtek.
  - **LC3-SWB is restricted to alt 6** ("ALT1/ALT5 modes don't appear to work … output is garbled").
  - Quirks disable LC3-A127 on MediaTek MT7925-family USB IDs (`0e8d`, `0489`, `13d3`, `2c7c`).
  - This machine's AX201 has alt 6 [V], kernel 7.2 [V], so mSBC and LC3-SWB transport should be eligible [I].
- **[I] Android side:** AOSP HFP has code paths for LC3-SWB and aptX-SWB over HFP (`HeadsetStateMachine.mHasSwbLc3Enabled`), but enabling them is vendor-dependent. Expect mSBC (16 kHz) on most phones, and CVSD (8 kHz) as the fallback. Foner observed mSBC on a Samsung. https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/android/app/src/com/android/bluetooth/hfp/HeadsetStateMachine.java
- **[V] Echo:** `bluez5.hfp-hf.disable-nrec` defaults to false (backend-native.c:4111-4118), so the phone's NREC (noise reduction/echo cancellation) stays on. With desktop speakers and a mic, plan on PipeWire `module-echo-cancel` (WebRTC) [I].

## 4. Contacts and call history (PBAP)

- **[V] obexd `org.bluez.obex.PhonebookAccess1`** (BlueZ 5.87 doc dated Oct 2023), session bus, service `org.bluez.obex`.
  Flow: `Client1.CreateSession(dest, {"Target":"pbap"})`, then `Select("int", "pb"|"ich"|"och"|"mch"|"cch"|"spd"|"fav")`, then `PullAll(targetfile, {Format:"vcard30", MaxCount, Offset, Fields, ResetNewMissedCalls})` → a Transfer object. `List()`, `Pull()`, `Search("name"|"number", …)` also exist.
  https://git.kernel.org/pub/scm/bluetooth/bluez.git/tree/doc/org.bluez.obex.PhonebookAccess.rst?h=5.87
- **[V] Android serves `pb`, `ich`, `och`, `mch`, `cch`, `fav`** (`/telecom/*` and `/SIM1/telecom/*`). Source: AOSP `BluetoothPbapObexServer.java` lines 120-160 (main branch, fetched 2026-11-04).
- **[V] Permission flow:** each device has a stored phonebook permission (ALLOWED / REJECTED / UNKNOWN). If it is UNKNOWN, Android broadcasts `ACTION_CONNECTION_ACCESS_REQUEST` (`REQUEST_TYPE_PHONEBOOK_ACCESS`), which shows a dialog. **The dialog times out after 30 s** (`USER_CONFIRM_TIMEOUT_VALUE = 30000`). The answer persists, so the dialog appears once per pairing.
  Source: `BluetoothPbapService.java:105-129, 297-304, 912-945`.
  Settings shows a per-device toggle, "Allow access to contacts and call history", next to "Phone calls" and "Media audio" (AOSP SettingsLib strings).
  If access is rejected, expect `org.bluez.obex.Error.Forbidden`.
- [I] Vendor builds (Samsung, Xiaomi) sometimes word or gate this differently. handsfree-linux reports "requires permission on Android 12+; varies by manufacturer". https://github.com/PavelTarlev1/handsfree-linux

## 5. Gotchas

1. **Android sends call audio to the desktop even when you answer on the phone.** [I, standard HFP AG behavior] When the desktop is the active HFP device, the AG opens SCO for every call.
   **Mitigation [V]:** set `RejectSCO=true` (or configure `bluez5.telephony.default-reject-sco = true`), then call `Activate()` only when the user clicks "answer on desktop" or "move audio here".
   [I] Answering through `Call1.Answer()` while `RejectSCO=true` keeps audio on the phone. The app must clear `RejectSCO` or call `Activate()` after answering.
2. **Moving audio back to the phone.**
   - [V] PipeWire's API has no deactivate, and `RejectSCO` only affects the *next* SCO connection. Foner removed its "move to phone" button for this reason. https://github.com/AminBlg/kaller/blob/main/docs/STATUS.md
   - [V] **Android does respect an HF-initiated SCO release.** HeadsetStateMachine `AudioOn` logs "audio disconnected by remote" and moves to `Connected` on `AUDIO_STATE_DISCONNECTED`. Telecom `handleBtInitiatedDisconnect()` switches to the baseline route (earpiece, wired headset, or speaker), excluding Bluetooth. Sources: AOSP `HeadsetStateMachine.java:1693-1697` (main, 2026-11-04); Telecom `CallAudioRouteStateMachine.java:782-806`.
   - So the fix needs a way to close the SCO socket from the desktop. Options: a small upstream PipeWire patch adding `Deactivate()`; or [I] switching the card profile away from `audio-gateway` and back (this also drops A2DP and the SLC, so it needs a prototype); or the user taps "phone" in Android's in-call audio picker.
3. **A2DP coexistence [V].** A2DP and HFP share one PipeWire card profile (`audio-gateway`), so they coexist. Android tracks the active device separately for A2DP and HFP (AOSP ActiveDeviceManager rule 3). The user can turn off "Media audio" for the desktop and keep "Phone calls".
   Tether found that iPhones need `a2dp_sink` before they offer HFP. This was not verified for Android.
4. **Earbuds and desktop connected together [V].** Android allows up to 5 connected audio devices (`config_bluetooth_max_connected_audio_devices = 5`; sysprop `persist.bluetooth.maxconnectedaudiodevices`, range 1-5). But **only one HFP device is active**, and the last connected or last activated one wins. If earbuds connect after the desktop, calls go to the earbuds. Call control from the desktop still works, because AT commands go to any connected HF [I].
   Sources: AOSP `AdapterProperties.java:71-74`, `res/values/config.xml:173`, `ActiveDeviceManager.java` header.
5. **Who opens the link.** BlueZ's built-in HFP (experimental, 5.86+) and PipeWire race for `0000111e` (§2). Tether also found that a desktop-initiated `ConnectProfile("0000111e")` fails when the phone advertises only `0000111f`, so the phone had to initiate (measured on iPhone, BlueZ 5.87). [I] Android usually reconnects HFP on its own after pairing.
6. **The service lives inside WirePlumber.** A WirePlumber restart drops and recreates `org.pipewire.Telephony` and all AG and call objects. Watch `NameOwnerChanged` [V: the bus name is owned by the wireplumber PID].
7. **No signal, battery, or operator indicators** through PipeWire [V].
8. **Emergency calls and USSD:** `Dial` passes the string as is. The USSD reply appears only on the handset (Foner STATUS) [secondary].

## 6. Why not a Wi-Fi relay with a companion Android app

- **[V] Third-party apps cannot capture call audio.** Capturing `VOICE_CALL`, `VOICE_UPLINK`, or `VOICE_DOWNLINK` "requires the `CAPTURE_AUDIO_OUTPUT` permission. This permission is reserved for use by system components and is not available to third-party applications." https://developer.android.com/reference/android/media/MediaRecorder.AudioSource (fetched 2026-11-04)
- **[I] There is also no public API to inject audio into the cellular uplink.** No AudioSource or AudioTrack usage targets the modem TX path for non-system apps.
- **[V] What a non-system app can control:**
  - `TelecomManager.acceptRingingCall()`: added API 26, **deprecated API 29**. Requires `ANSWER_PHONE_CALLS` or `MODIFY_PHONE_STATE`. `endCall()` is also deprecated in API 29; the docs point wearable companion apps to `InCallService` and call screeners to `CallScreeningService`. https://developer.android.com/reference/android/telecom/TelecomManager
  - `InCallService` binds only for the **default dialer** (`ROLE_DIALER`; it must provide full incoming-call and in-call UI and handle `ACTION_DIAL`), or for a **companion app for a wearable** (`MANAGE_ONGOING_CALLS` + CompanionDeviceManager association). https://developer.android.com/reference/android/telecom/InCallService
  - `CALL_PHONE` lets an app place calls without dialer confirmation.
  - Net result: a relay app could ring, answer, hang up, and dial, but the voice would still play on the phone's earpiece. A Bluetooth HF is the only non-root path that carries the voice.

## Recommendation

**Stack:** BlueZ 5.87 (stock, *without* `--experimental`) + PipeWire ≥1.4 native backend with `hfp_hf` (default) + **`org.pipewire.Telephony`** for call control + **obexd `PhonebookAccess1`** for contacts and call history + our own UI daemon (session-bus D-Bus client, Hyprland layer-shell or notification UI). No Android app, no oFono, no AT-command code.

Concrete config (`~/.config/wireplumber/wireplumber.conf.d/60-desktop-calls.conf`):
```
monitor.bluez.properties = {
  bluez5.roles = [ a2dp_sink a2dp_source bap_sink bap_source hfp_hf hfp_ag ]
  bluez5.telephony.default-reject-sco = true   # audio stays on phone until user opts in
}
```
Packages to add: `bluez-obex`. Optionally load PipeWire's echo-cancel module for speaker use.

App logic:
1. Watch `/org/pipewire/Telephony` (ObjectManager) for AGs.
2. On each AG, watch `InterfacesAdded` and `PropertiesChanged` for `Call1`.
3. For an incoming call, look up `LineIdentification` in the PBAP cache and show a notification.
4. On "Answer here": call `Call1.Answer()`, then `AudioGatewayTransport1.Activate()`.
5. On "Answer on phone": do nothing; `RejectSCO` keeps audio on the phone.
6. Dial with `AudioGateway1.Dial()`. Pull `pb` and `cch` on connect.

**Top risks**
1. **No "send audio back to phone."** PipeWire's API has `Activate()` but no `Deactivate()`. Android handles an HF-side SCO release correctly (verified in AOSP), so the fix is a small upstream PipeWire patch, or a profile-toggle workaround that needs a prototype.
2. **The HFP active-device and UUID fights.** Android routes calls to the last-activated HFP device (earbuds vs desktop). If BlueZ's experimental built-in HFP (5.86+) is ever enabled, it competes with PipeWire for UUID `0000111e`. Detect this at startup and tell the user.
3. **Thin field validation.** The Telephony API dates from 2025-03, has one main author (Collabora), and is tested in public on only a handful of handsets. Expect per-vendor quirks (Foner's `Call1.Hangup` anomaly, PBAP prompts, codec fallback to CVSD), and track PipeWire minor releases.
